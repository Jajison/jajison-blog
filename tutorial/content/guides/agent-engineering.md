# Agent 工程：把工具循环变成可控制、可恢复的系统

**这一课做成什么**：运行一次带真实工具结果与停止原因的循环，再明确如果用模型替换决策部分，哪些校验仍必须由程序负责。

**Agent**根据目标和观察选择行动；**运行环境或 Harness**负责执行与控制；**工具**完成一个具体动作。把三者分开，才容易定位“模型选择错了”与“工具执行失败”。本课采用模型决定动态路径的定义；不同系统也会使用更宽的 Agent 定义。[工作流与 Agent 的架构区分](https://www.anthropic.com/engineering/building-effective-agents)

## 用状态机把“进行中”拆开

**状态机**是列出允许状态与转移规则的程序结构。例如：

~~~text
ready → deciding → validating → executing → observing
          ↑                                  │
          └────────────继续───────────────────┘
          └→ completed / needs_input / stopped / failed
~~~

deciding 是提出下一步；validating 是检查工具、参数、权限与剩余预算；executing 才真的运行；observing 记录实际返回。completed 必须有验收依据。模型说“好了”只能触发验收，不能直接绕过它。

下面是**设计示例**，不是练习程序的完整持久化格式：

~~~json
{
  "task_id": "report-demo-01",
  "status": "observing",
  "input_version": "records-v1",
  "calls_used": 1,
  "max_calls": 2,
  "last_observation": {
    "tool": "search_notes",
    "status": "ok",
    "evidence_ids": ["event-guide.md:L3"]
  }
}
~~~

任务状态保存“做到哪里”；事件日志保存“实际发生过什么”；模型上下文只挑当前决策需要的部分。长对话全文不是一个便于恢复的状态结构。

## 工具契约把自由文字变成可执行请求

**schema**描述字段、类型、允许值与必填条件。模型可提出：

~~~json
{"tool": "search_notes", "arguments": {"query": "报名 截止", "limit": 3}}
~~~

执行层要验证工具名在允许列表中、query 非空且有长度上限、limit 是范围内整数；随后构造参数调用固定实现。不要把整段模型文字交给 shell，也不要让资料文本指定任意函数名。

输出也需要契约：成功可返回候选列表；无结果应明确为空；超时与参数错误要区分。一个 HTTP 200 响应还可能含业务错误，一个有效 JSON 也可能引用不存在的文件。契约至少覆盖传输、结构和业务含义三层。

## 接 MCP 时发生了什么

MCP 中，**host**是承载用户交互与模型的应用；**client**负责与某服务器建立协议连接；**server**提供工具、资源或提示模板。这是接入层，不规定你的业务状态机必须怎样写。

以 2025-06-18 版规范为例：先 initialize 交换协议版本与能力，客户端发送 initialized 通知后进入正常操作；支持工具的服务器可响应 tools/list 与 tools/call。协议版本和客户端支持范围要核对，不能因为服务器存在就假设所有特性可用。[MCP 架构](https://modelcontextprotocol.io/specification/2025-06-18/architecture)、[生命周期](https://modelcontextprotocol.io/specification/2025-06-18/basic/lifecycle)

本地 stdio 连接和远程 HTTP 连接涉及不同启动、身份与部署方式。协议消息验证、服务身份验证、业务权限是不同层的检查；“成功连接”不能证明某个动作已经被用户授权。

## 重试之前，先知道是否已经生效

**幂等**指重复相同逻辑请求不会增加额外副作用。读取资料通常易于重试；“创建工单”超时后，服务器可能已经创建成功，只是响应没回来，再发一遍可能重复创建。

一种做法是为一次逻辑操作使用稳定的请求 id，由服务记录结果；同一个 id 重试时返回已有结果，并校验参数未变化。超时后的状态应记为“结果未知，待核对”，不能直接当作“没有执行”。这需要服务和存储协作，单靠模型承诺无效。[AWS：让重试安全的幂等 API](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

网络暂时失败可以在总预算内等待后重试；参数非法要修参数；权限不足要停止或转给有权限的流程。同一错误重复发生时，没有新信息的循环通常不值得继续。

## 时间、权限与上下文分别设边界

**调用预算**限制动作数量，**截止时间**限制墙钟时长，**token 或费用预算**限制模型消耗，三者不能互相替代。一次调用也可能等待很久。给子进程或网络请求设置超时后，还要检查底层是否实际终止，以及是否已产生外部副作用。

权限应落实到可调用工具、可读写目录、网络去向和服务凭据；提示词中的“只读”不是文件系统隔离。工具输出与检索资料应作为观察数据，不能自行修改这些权限。

**长期记忆**是跨任务保存的可检索信息。它需要来源、时间、适用范围、修改与删除方式；保存“用户喜欢简短报告”与保存“上次调用工具返回了 90”是不同用途。摘要压缩会丢细节，应保留原始证据位置；状态变化时不能把过期偏好或猜测永久当事实。

## 动手：运行一个真实受控循环

在 ai-workshop 根目录运行，Windows 将 python3 换为 py -3：

~~~sh
python3 controlled_loop.py "什么时候停止报名？"
python3 controlled_loop.py "什么时候停止报名？" --max-calls 1
python3 controlled_loop.py "餐费 报销"
python3 controlled_loop.py "报名 截止" --timeout 0.000001
~~~

策略是公开的固定规则：先原样关键词检索，无结果时从问题中抽取预设关键词，再试一次。**它没有调用 LLM，也不生成答案**；它让你能独立测试工具执行与控制，再讨论模型是否值得接入。

第一条预期两次调用后得到候选，停止原因为 evidence_found；第二条只有一轮预算，停止原因为 budget_exhausted；第三条应为 no_result；极短时间预算应为 timeout。实际日志含 calls_used、events、evidence 与 stop_reason。找到候选不等于通过事实验收。

~~~sh
python3 controlled_loop.py "报名 截止" --output output/loop.json
~~~

这会保存新的 JSON 日志，拒绝覆盖同名文件。现有练习只控制固定搜索子进程，**没有通用系统沙箱、跨进程恢复、模型计费或写操作幂等存储**。日志可供检查，不能把重新运行命令描述为从断点恢复。

## 从日志到恢复，还差哪一步

假设未来系统写报告后崩溃，恢复时先查任务 id 对应输出是否已经存在、内容校验是否通过，再决定继续或补做。保存检查点时记录输入版本、工具版本、已确认结果与尚未知操作；不要只写“第 3 步”而没有事实依据。

接入真实模型时，用模型适配器替换固定策略，保持校验、超时、日志与验收层不变。新增的测试应包含错误工具名、错误参数、伪造来源、重复请求与预算耗尽。多 Agent 则额外需要任务划分、结果合并和共享状态冲突管理，不能只把角色提示复制几份。

**完成标准**：解释四种真实停止原因；指出工具调用意图、实际执行和验收完成的区别；为一个可能重复写入的动作设计请求 id 与核对流程，并标注哪些机制尚未实现。

<details>
<summary>自测：有完整聊天记录，就一定能安全恢复任务吗？</summary>

不一定。记录可能写着“准备创建”却没有实际结果，也可能丢掉响应而外部已成功。恢复需要可核对的操作 id、状态、结果与版本；对未知副作用先核对，不能盲目重新执行整段历史。
