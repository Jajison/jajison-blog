# 测试与持续交付：让每次改进都有可复查的结果

**这一课做成什么**：为资料助手建立四层检查，理解哪些可以自动阻止发布，哪些仍需要真实模型或浏览器观察，最后写一份可交接的验证记录。

**测试**通过规定输入与预期检查程序行为；**评估**衡量模型或系统在样本集合上的表现；**回归检查**在改动后重跑已有用例，确认原有行为没有退步。名称可以交叉，但执行对象、判据与证据必须写清。

## 从一个具体故障拆开测试层

假设用户问报名截止，系统返回错误日期。可能是 JSON 解析错、检索漏证据、模型忽略证据，也可能浏览器展示了上一次缓存答案。只做“页面能打开”无法定位它。

| 层 | 输入与判据 | 可以发现什么 |
| --- | --- | --- |
| 单元 | 四条记录 → 120 总分钟、90 完成分钟 | 计算口径与字段校验 |
| 集成 | 查询词 → 文件行号与原文 | 模块衔接、检索与来源错误 |
| 模型评估 | 问题+证据 → 答案与引用 | 幻觉、遗漏、错误拒答 |
| 端到端 | 用户提交 → 界面结果 → 导出文件 | 状态、交互、保存与部署问题 |

**单元测试**聚焦一小块行为，**集成测试**连接多个模块，**端到端测试**从用户入口走到结果。对模型调用使用固定的模拟返回，适合验证程序处理逻辑；必须写明模拟，不能把它当成模型真实通过。[Python unittest](https://docs.python.org/3/library/unittest.html)

## 写会抓住错误的断言

**断言**是可执行的“应当如此”。对于报告工具，检查程序退出码只是第一步；还应检查数值、输出内容、原输入没有变化、已有结果没有被覆盖。

~~~python
import unittest
from report import render

class ReportRuleTests(unittest.TestCase):
    def test_pending_does_not_count_as_completed(self):
        rows = [
            {"id": "A", "task": "写初稿", "status": "done", "minutes": 45},
            {"id": "B", "task": "确认场地", "status": "pending", "minutes": 30},
        ]
        result = render(rows)
        self.assertIn("总耗时：75 分钟", result)
        self.assertIn("已完成任务耗时：45 分钟", result)

if __name__ == "__main__":
    unittest.main()
~~~

在 ai-workshop 根目录另存为 test_report_rule.py，运行 python3 test_report_rule.py；Windows 使用 py -3。这个测试能抓住“把 pending 也算入已完成”的错误，不要求报告排版每个字符都固定。它没有检查输入验证函数；重复 id、负数、布尔值等需要另外覆盖。

对排序无关的输入，可以增加**变形检查**：交换记录顺序，总数应不变；只增加待办分钟，已完成分钟应不变。这类检查利用任务关系，补充逐个固定样例。

## 模型评估要保留失败类型

每个用例至少包含原输入、可用证据、预期事实、允许的不确定性、关键失败规则。事实题可以逐字段评分；开放写作可用明确量表与人工比较；模型评分可以辅助，但需要用人工样本校准，检查偏爱长答案或固定风格的问题。

把问题按清晰事实、缺信息、同义改写、冲突、工具故障、越界要求分组。一个系统可能普通问题更好、无答案问题更差；只看总均值会掩盖这种变化。不要为了提升分数删除失败样例。

开发时反复使用的样例会影响提示与实现，另外保留未参与修改的测试集。发生真实失败后，可脱敏并加入回归集，同时补新的保留样例。相似文档或同一模板的改写应考虑放在同一拆分侧，避免近重复泄漏造成虚高。

## 动手：比较两种检索预算

从 ai-workshop 根目录运行：

~~~sh
python3 evaluate_retrieval.py --limit 1 --output output/eval-k1.json
python3 evaluate_retrieval.py --limit 3 --output output/eval-k3.json
~~~

先比较逐例 retrieved 与 expected，再看汇总。默认样本中 k 从 1 到 3，Recall 从 0.6 提升到 0.8，Precision 从 0.8 降到 0.4；这说明更多相关证据被找到，也加入了更多非相关位置。它没有测量生成答案、费用或用户满意度，不能直接宣称 k=3 的整个系统更好。

接下来手动选择一条已知事实和一条无答案题，把候选交给你能使用的 AI 工具。记录模型、日期、完整提示、答案、出处和通过原因。两份 JSON 是自动检索实验，后两条才是真实模型观察；记录里分别列出。

## CI 怎样变成发布门槛

**CI（持续集成）**在代码变动时自动执行一组检查。GitHub Actions 中，事件触发 workflow，workflow 包含 job，job 在 runner 上按 step 执行。它不会自动知道正确业务规则，需要维护者把已有检查写进去。[GitHub Actions](https://docs.github.com/en/actions/get-started/understand-github-actions)

对于这个练习，合理顺序是：安装固定依赖 → 确定性测试 → 内容与链接检查 → 构建 → 输出检查。外部模型评估若需要费用或凭据，可单独设置按需门槛，并记录对应版本；不要用空响应假装通过。

检查应产生可靠退出状态：测试失败时返回非零，不要用“忽略错误继续”的配置把失败标绿。CI 通过证明的是该次代码、环境和用例组合通过，不能证明所有浏览器、操作系统和输入都已覆盖。

## 发布、观察与回滚是一段完整过程

**构建产物**是准备发布的文件，**部署**是把产物放到用户访问环境；本地构建成功与公开服务正常是两个观察。部署后至少用真实入口走一条核心流程，并核对版本、资源路径和数据边界。

**回滚**是将服务恢复到已知可用版本。静态页面可保留前一个产物；数据库结构、写入数据和外部动作却不一定能随代码一起回退。修改字段前应设计迁移与兼容，不能把“重新部署旧代码”当成所有数据操作的撤销。

上线后的日志可记录错误类别、用时、重试与验收失败，但不应无差别保存完整私密输入。监控指标对应真实问题：资料助手关注无证据回答、检索空结果与超时；报告工具关注非法输入和保存失败。

## 留下别人能复查的一页记录

~~~text
版本：代码 revision、数据/索引版本、依赖与模型标识
范围：本次改变了什么，哪些行为必须保持
已执行：命令、输入、实际结果、结果文件位置
失败：样例、症状、归属环节、复现方式
未验证：目标浏览器、操作系统、真实模型或外部服务
发布检查：真实入口与核心流程观察
恢复方法：可用产物、数据备份与不能自动撤销的动作
~~~

没有执行的项标“未验证”；执行了但失败的项标“失败”，两者含义不同。完成标准要允许明确失败，而不是只保留好看的数字。

**完成标准**：运行本文单元测试与两份检索实验，解释指标取舍；为一个模型失败和一个程序失败选对检查层；交付记录中能找到原始证据与未验证项。

<details>
<summary>自测：模型升级后，原来的程序单元测试都通过，能否跳过模型评估？</summary>

不能。单元测试可能用固定文本或模拟响应，验证的是代码规则；新模型可能改变结构化输出、拒答、引用与工具选择。保持确定性测试，同时在相同代表问题上重跑真实模型评估，才能分清变化来自哪里。

</details>
