# Workflow 与 Agent：谁决定下一步

**这一课做成什么**：能判断任务适合固定工作流还是 Agent。

自动生成周报，可以是脚本，也可以是工作流，未必需要 Agent。这里最有用的区分是：**下一步由预先写好的规则决定，还是由模型根据现场结果决定？**

## 固定步骤，适合工作流

~~~text
读取记录 → 检查字段 → 计算汇总 → 请 AI 润色 → 人工核对
~~~

这条路线事先知道每一步要做什么，即使其中有 AI，也可以称为 Workflow（工作流）。前面的报告脚本连模型都不需要，就能完成固定计算。

## 现场决定，才需要更灵活的循环

如果任务是“查清某个工具为什么启动失败”，第一步可能是读说明，也可能是看报错。之后是否检查依赖、运行命令、修改配置，要依据返回结果决定。

![Agent 在目标、选择工具、执行和观察之间循环，并受到预算和停止条件限制](../assets/agent-loop.svg)

在本教程中，**Agent**指让模型根据目标和反馈，选择下一步操作的系统。不同产品对这个词的定义会略有不同。

## 一个够用的循环

1. 读取任务与当前状态。
2. 决定回答，或提出一个工具调用。
3. 由外部程序执行工具，并返回真实结果。
4. 根据结果更新状态，继续或停止。

模型说“我检查了文件”，不代表执行过检查。要有实际读取、命令返回或其他可观察结果。一次调用失败，也不能仅凭计划里写着“完成验证”就算成功。

## 怎样选

| 情况 | 从什么开始 |
| --- | --- |
| 同一格式的数据，每周同一口径 | 脚本 |
| 步骤固定，但其中一步需要语言能力 | 工作流 |
| 路径随反馈变化、事先很难写全分支 | 单个 Agent + 少量工具 |
| 单个 Agent 已能完成 | 先不要增加多智能体 |

Agent 的灵活性会增加工具调用、等待和出错机会。先证明固定方案不够，再扩大自由度。

## 动手做

让 AI 分别设计“每周汇总同一个 JSON 文件”和“排查一个未知网页错误”的步骤。标出哪些步骤固定、哪些要等实际反馈才能决定。

再给第二个任务补停止条件：“修复一项指定错误；最多两轮修改；仍失败则保留现场，说明阻碍。”实际执行时，还需工具环境落实这些限制。

**完成标准**：能说清自己是否需要模型决定下一步，而不是因为工具名里有 Agent 就使用它。

<details>
<summary>自测：用了五个 AI 调用，就是多智能体系统吗？</summary>

不是。它可能只是五步固定工作流。调用次数、角色数量和决策方式是不同维度。
