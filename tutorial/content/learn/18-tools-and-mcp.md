# 工具、MCP 和 Skill：让 AI 接上实际工作

**这一课做成什么**：能描述一个工具的输入输出，并理解 MCP 与 Skill 的位置。

AI 可以写一句“已经找到文件”，也可以真的调用搜索。两者的区别，在于后者连接了一个由程序执行的工具，并取得返回结果。

## 工具要说清输入和输出

假设提供 search_notes 工具：

~~~text
用途：只在指定资料目录中搜索文字。
输入：query，搜索词；limit，最多返回几条。
输出：文件名、行号、匹配片段。
失败：目录不存在或没有匹配时，返回明确状态。
权限：只读，不写文件，不发送消息。
~~~

模型生成调用意图，外部程序负责执行，再把结果交回模型。**Function Calling（函数调用）**常用于让模型按规定格式表达这个意图；它不等于函数已经执行成功。

## MCP 解决接入标准

**MCP（Model Context Protocol）**是一种让 AI 应用连接外部工具和数据的开放协议。可以把它理解为标准接口：接入双方按约定交流，减少每个工具单独适配的工作。

它不自动赋予模型更高智力，也不保证每个服务器可靠。连接某个服务前，要知道它访问什么、能执行什么，以及当前客户端是否支持相应能力。

写一个本地脚本不需要先搭 MCP。工具数量增多、需要在多个 AI 应用间复用时，标准化接入更有价值。

## Skill 解决可复用做法

在很多 AI 工具中，**Skill（技能）**是可复用的操作说明与资源包，可能包含文档、示例、脚本。比如“周报整理”技能告诉 AI：先读取记录，再检查字段、生成报告、核对数字。

具体格式与加载方式依产品而定。加载一个 Skill 通常不等于重新训练模型；写在说明里的权限边界，也不自动成为操作系统的硬限制。

| 名称 | 主要回答 |
| --- | --- |
| 工具 | 可以执行什么动作？输入输出是什么？ |
| MCP | 应用怎样按统一协议接入工具与资料？ |
| Skill | 这类任务通常应该怎样完成？ |
| Harness | 怎样记录、约束和管理整个运行过程？ |

## 动手做

为上一课的 report.py 写一张工具说明，只包括用途、输入、输出、失败、权限。然后把“每周先预览、再核对总数、最后保存”的步骤写成一张操作卡。现在不需要打包成真正的 Skill 或 MCP 服务器。

**完成标准**：能把“能调用的动作”和“推荐怎么做”分开，不会以为装了一个插件就自动完成整个业务。

<details>
<summary>自测：MCP 与 API 是互相替代的吗？</summary>

不必然。一个 MCP 服务器可以在内部调用已有 API，再用统一形式向 AI 应用提供工具。两者处在不同的接口层。

</details>
