# 从能打开到能交付：测试、发布和交接

**这一课做成什么**：能验收网页并说明发布后的数据边界。

页面能打开，只说明它成功显示了。要交付给别人，还需要确认输入、保存、异常和再次使用都符合预期。

## 用这张表验收待办网页

| 操作 | 预期 |
| --- | --- |
| 输入空格后新增 | 不新增空任务，给出提示 |
| 新增三条，勾选一条 | 总数 3，已完成 1 |
| 刷新相同地址 | 内容和勾选状态保留 |
| 导出 JSON | 文件里有三条以及完成状态 |
| 缩窄浏览器到手机宽度 | 按钮可点，正文不超出页面 |
| 浏览器禁止本地保存 | 告知未持久保存，仍可导出当前内容 |

最后一种情况要在独立测试环境检查，不要为了练习清理自己其他网站的数据。

## 给 AI 的验证要求

~~~text
请逐项检查上面的验收表。
每项记录：操作、观察到的结果、通过或失败。
区分“实际在浏览器操作过”和“仅阅读代码推测”。
未运行的检查写未验证，不用“应该没问题”代替结果。
~~~

运行自动化测试有帮助，但这一版先把关键用户流程走通，比写大量只检查代码存在的测试更有价值。

## 本地运行与公开发布

GitHub 仓库主要保存文件，GitHub Pages 则把选定内容作为静态网页提供访问。静态网页可以运行浏览器 JavaScript，但不能在 GitHub Pages 上运行 Python 后台或安全保存服务端密钥。

对这个单文件练习，最小发布过程是：

1. 在 GitHub 建一个专门的练习仓库，确认是否公开。
2. 把已验收的 todo.html 作为仓库根目录的 index.html 上传。
3. 在 Settings → Pages 选择 Deploy from a branch，并选择实际存放页面的分支和根目录。
4. 等部署完成，打开 Pages 提供的真实地址，重新执行新增、刷新和导出检查。

博客框架的构建发布可能使用 GitHub Actions，那是另一种流程；不要把单文件练习的设置直接套到框架博客。

## 发布后，数据发生了什么

页面地址公开后，访问者可以加载页面。示例的待办仍保存在每个人自己的浏览器里，不会自动变成共享清单。localhost 下保存的记录也不会自动迁移到 GitHub Pages 地址，因为它们的站点来源不同。

后面需要跨设备同步时，再规划后台、存储和登录。不要把密钥嵌进页面来“临时解决”。

## 留一张交接卡

交付时写清用途、打开方式、数据存放位置、如何导出、已知限制，以及出了问题找哪一份源文件。未来的你也会用到它。

**动手做**：完成本地验收表，并写一段 100 字以内的使用说明。公开发布是可选练习，不是进入下一阶段的前提。

**完成标准**：能解释哪些流程实测通过、哪些功能尚未提供，以及数据是否离开电脑。

<details>
<summary>自测：为什么部署完成后还要再验收一次？</summary>

网址、路径和浏览器来源变化可能影响资源加载与本地保存。本地成功不能代替对实际访问地址的检查。

</details>
