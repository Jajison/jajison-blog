# 怎样知道 AI 真的变好了：十个样例就能起步

**这一课做成什么**：能建立一套可重复的小型验收样例。

昨天一句提示词很好用，今天换了材料却漏掉关键项。一个惊艳的回答不能证明流程稳定。最实用的起点，是固定一小组问题，每次改动后再跑一遍。

这就是**评估（evaluation，常简称 eval）**：按事先定义的标准比较结果。

## 样例要有容易的，也要有不该回答的

以资料助手为例，十个用例可以包括：明确事实、精确数字、同义问法、完全无关的问题、资料缺失、冲突、提示注入、第一次检索失败、超过预算和正常交付。

项目三附有 [十个验收用例](../downloads/workshop/eval-cases.json)。其中部分是人工或模拟运行情境；它们不是声称离线脚本已经实现了全部 Harness 能力。

## 先写标准，再看答案

| 维度 | 怎样记录 |
| --- | --- |
| 正确性 | 必须出现什么事实；哪些内容不能编造 |
| 证据 | 来源是否真实存在，是否支持结论 |
| 完整性 | 有没有遗漏必要条件或例外 |
| 边界 | 证据不足时是否承认，不该执行时是否停止 |
| 代价 | 用时、工具调用数、可获得的费用记录 |

总分并不是唯一标准。一次虚构金额，可能比三次措辞不够自然更值得优先处理。对这类关键失败单独标记。

## 一次只改一个因素

先记录方案 A，再改变提示词、检索规则或模型其中之一，运行相同用例得到方案 B。记录当时的输入、模型标识、日期和参数；不能把不同材料的两次结果直接当作公平比较。

把十题从 7 题通过变为 9 题通过，可以作为这组样例上的改善证据，不能直接宣布真实任务正确率达到 90%。样本小，内容也未必代表所有工作场景。

对开发中反复使用的样例会逐渐“调得很熟”，因此还要保留几个没参与修改的新问题，检查方法是否能迁移。

## 允许明确的失败

网络失败时可以重试；同样错误持续出现时，要停止并保留原因。资料没有写明时，说不知道比猜一个答案更符合目标。

不要为了让通过率好看，把难题删掉或把拒答一律算失败。标准应当反映实际用途。

## 动手做

选项目三的前三个事实题和两个证据不足题，填写“预期、实际、来源、结果”。改进一次提示卡，再比较差异。人工填写真实观察，不要让 AI 代填没有执行过的实验。

**完成标准**：能说“在哪些任务上变好了、代价是什么、还有什么没解决”，而不只是“感觉更聪明”。

<details>
<summary>自测：同一个模型给自己的回答打满分，可以作为通过依据吗？</summary>

只能当辅助信息。它可能没发现自己的错误。确定性的规则、来源核对、实际运行以及必要的人工判断更可靠。
