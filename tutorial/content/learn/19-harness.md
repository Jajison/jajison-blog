# Harness：用状态、边界和记录管理 AI 的运行

**这一课做成什么**：运行带调用次数、超时和日志的资料检索循环，区分“程序落实的限制”与“只写在说明里的要求”，再为一个重复任务制定可执行的运行规则。

本教程把 **Harness** 理解为围绕模型组织的运行配套设施：工具执行、状态管理、权限、预算、日志、恢复与验收。这个词不是一个功能完全统一的产品规范，讨论时需要说清具体实现覆盖哪些职责。

## 先看一次任务需要谁负责

![Harness 在模型与工具周围管理任务、权限、预算、记录、状态和验收](../assets/harness.svg)

以工作报告为例，模型可理解需求或组织语言；确定性程序读取、校验与统计；运行层控制能操作什么和何时停止；验收步骤确认结果是否满足目标。真正的权限与预算应在模型之外执行。

| 规则 | 落实位置 | 如何观察 |
| --- | --- | --- |
| 只读取指定资料 | 工具接口和目录访问限制 | 访问不在范围内的资料被拒绝 |
| 不覆盖已有报告 | 排他创建文件 | 同名输出保持原内容并报错 |
| 最多两次搜索 | 控制器计数 | 日志调用数不超过上限 |
| 不无限等待 | 截止时间与工具超时 | 工具被终止，记录 timeout |
| 结果正确 | 确定性规则与来源核对 | 数值、原文、测试结果可复查 |

“执行完命令”与“报告正确”不是同一状态。实际环境反馈和明确停止条件是可靠工具循环的基础。[Agent 的环境反馈与停止](https://www.anthropic.com/engineering/building-effective-agents)

## 提示要求怎样变成程序约束

“请不要覆盖文件”是模型应遵守的行为要求；report.py 使用排他创建，重名时返回错误，是程序保护。若模型还拥有另一个任意写文件的工具，就可能绕开这一个脚本的保护；更强的边界需要覆盖全部工具和底层访问权限。

“最多两分钟”也有不同实现：在提示词里写数字、循环前查看时间、对子进程设置剩余时间超时，它们的保证不同。只在每轮开始看表，不能阻止一个已经卡住的工具长期运行。网络请求超时也不保证远程业务没有完成，应另行核对外部状态。

为读者解释这些差别，是为了让配置可验证，而不是让每一步都征求意见。先约定允许独立完成的范围，只有信息不足或操作超出范围时才进入额外决策。

## 状态、日志、上下文与记忆分别保存什么

- **任务状态**：当前在检索、执行、待核对还是已完成，用于决定下一步。
- **事件日志**：真实调用、参数摘要、时间、错误、结果位置，用于排错与审计。
- **模型上下文**：当前这次决策能看到的指令和信息，长度有限。
- **长期记忆**：跨任务复用的事实或偏好，需要来源、时间、范围与纠错方式。

“用户喜欢简短周报”可以是偏好记忆；“某次文件写入是否成功”应该有具体操作结果，不能仅存在一段容易丢失的对话总结中。日志也不必保存所有敏感原文，可以保留必要标识与脱敏摘要。

压缩上下文时，保留关键输入标识、已验证事实、未知事项和输出路径。把“还未检查预算”压成“预算已处理”会改变任务事实。总结不是新的证据来源。

## 动手：让限制真正发生

在 ai-workshop 根目录执行，Windows 把 python3 换成 py -3：

~~~sh
python3 controlled_loop.py "什么时候停止报名？" --max-calls 1
python3 controlled_loop.py "报名 截止" --timeout 0.000001
python3 controlled_loop.py "报名 截止" --output output/loop.json
~~~

第一条预期 budget_exhausted：完整问句没有匹配，预算不足以换关键词再查。第二条用极短预算演示 timeout；实际调用数可能是 0 或 1，取决于时钟检查发生的位置，但不应报告已经完成检索。第三条找到候选并保存新日志；再次写同一路径应拒绝覆盖。

这个控制器使用固定策略和固定检索子进程，**没有调用模型**。它真实实现调用次数与工具循环时间限制，也保留事件与候选；没有实现通用文件系统沙箱、长期记忆服务、外部写操作或断点恢复。边界应按代码实际能力填写。

## 从运行日志作出正确判断

打开 output/loop.json，查看 calls_used、stop_reason、events、evidence。evidence_found 表示候选存在，不等于最终答案正确；no_result 表示当前策略没找到候选，不证明原始资料全无答案；budget_exhausted 与 timeout 表示被限制终止，也不能伪装成成功。

工具循环的进程成功返回，还可能交付“未找到证据”的正常业务结果。反过来，工具出现读取错误时，应保留错误原因，让上层知道不能继续把空返回当作已完成检索。

对真实 Agent，可以把“模型请求结束”作为进入验收的信号。验收未通过时记录失败或明确继续条件，不能让模型一句“完成”自动消除未解决事项。

## 给自己的任务写一张运行卡

~~~text
目标：根据本周记录生成可核对的报告
允许输入：指定 JSON 文件及其版本
允许动作：读取、校验、计算；结果写入新输出文件
预算：工具调用上限、截止时间；若调用模型另设费用规则
异常：非法输入立即停止；临时失败在剩余预算内重试
状态：待校验 / 已计算 / 待核对 / 已交付 / 失败
验收：4 条、3 完成、120 总分钟、90 完成分钟；源文件未变
交接：结果路径、实际检查、尚未验证项
~~~

上面数字只适用于原始练习输入；换资料时必须更新预期，不能把固定数字作为万能验收规则。每一条规则旁标注它由哪个程序或人工动作落实，找出仍只存在于文字里的部分。

**完成标准**：能从日志说明任务是得到候选、未找到、超时还是耗尽预算；验证保存拒绝覆盖；能区分实现了的机制、设计中的机制和仍由人判断的业务事实。

<details>
<summary>自测：保存了 loop.json，关闭电脑后重跑命令就算断点恢复吗？</summary>

不算。当前程序重新开始一次运行。真正恢复需要读取已保存状态，核对输入版本、已完成动作和未知副作用，避免重复操作，并从明确检查点继续。日志是恢复的材料，不自动提供恢复逻辑。

</details>
